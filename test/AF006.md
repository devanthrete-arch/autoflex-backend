# AF-006 returning walk-in API regression

`returning-walk-ins.e2e-spec.ts` runs the same API scenarios against the memory
adapter and an explicitly isolated PostgreSQL database. The PostgreSQL mode also
runs transaction, concurrency and migration checks that the memory adapter cannot
prove.

## Memory API

```sh
npm run test:e2e -- --runInBand --testPathPatterns=returning-walk-ins
```

The common scenarios cover staff authorization and center isolation, minimal
lookup projections, normalization and ambiguous legacy records, selected customer
and vehicle revisions, blind ownership conflicts, account-link handoff, vehicle
type and availability, exact retry and result recovery, saved identity, and
booking conversion with its saved service scope.

The test-only `seedReturningWalkIn` helper creates an already linked record. It
does **not** implement user registration, verified account linking or RC
verification. Those are separate product/integration work.

## Isolated PostgreSQL

The target is fixed at `127.0.0.1:55406`, user/database `af006_test`. The suite
checks the database identity before resetting its schema and does not read the
workshop's connection settings. Do not run two copies of this suite against the
same disposable database at the same time.

```sh
docker run --name autoflex-af006-test --label autoflex.test=af006 \
  -e POSTGRES_USER=af006_test -e POSTGRES_PASSWORD=af006_test \
  -e POSTGRES_DB=af006_test -p 127.0.0.1:55406:5432 -d postgres:16-alpine

docker exec autoflex-af006-test pg_isready -U af006_test -d af006_test

AF006_POSTGRES_TEST=true npm run test:e2e -- --runInBand \
  --testPathPatterns=returning-walk-ins

docker rm -f -v autoflex-af006-test
```

Additional PostgreSQL assertions cover:

- Audit and receipt persistence failures roll back the entire command, including
  a new vehicle or an explicit type confirmation; an identical retry can succeed.
- Overlapping identical retry keys commit one visit. Independent keys cannot
  create two active visits for the same center vehicle.
- Failed booking conversion preserves booking state, customer/vehicle links,
  garage odometer and the saved package scope.
- Stale customer cancellation and desk decline, confirmation or no-show cannot
  undo a committed check-in. If cancellation wins, check-in creates no job.
- Migration triggers maintain canonical identity and revisions; type backfill
  uses a matching linked garage and does not infer type from old defaulted jobs.

The injected failure tests intentionally log server exceptions. A passing test
asserts the resulting rollback, rather than the absence of an exception log.

## Adapter limits

The memory adapter does not provide PostgreSQL transaction rollback, row locks or
trigger semantics. After a refused command it can retain an uncommitted receipt
insert. The common stale-selection check therefore verifies business rows in
memory and also verifies receipt rollback in PostgreSQL. Transaction and race
claims depend on the PostgreSQL run, not the memory result.

## Related regression changes

Older API fixtures now seed explicit linked center records, submit the selected
IDs/revisions with a stable key and fetch job detail separately when they need its
version or operational fields. Creation returns only `id`, `jobNumber` and
`status`. The reservation regression verifies that repeating check-in recovers
the attached job without changing the original check-in time or job count.
