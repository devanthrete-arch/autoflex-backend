# AF-009 scheduling verification

Run backend unit tests with `npm test -- --runInBand`; API coverage with `npm run test:e2e -- --runInBand --testPathPatterns=scheduling`.

## Disposable PostgreSQL gate

```sh
docker run --name autoflex-af009-test \
  -e POSTGRES_USER=af009_test -e POSTGRES_PASSWORD=af009_test -e POSTGRES_DB=af009_test \
  -p 127.0.0.1:55409:5432 -d postgres:16
npm run test:scheduling:postgres
docker rm -f autoflex-af009-test
```

The suite uses only `127.0.0.1:55409/af009_test`, checks the DB identity, and resets that disposable schema. Never redirect it to the workshop database. It tests 21 cases: permission/header gates, inherited defaults, breaks/closures/exceptional openings, malformed and forged slots, horizon/notice, schedule and booking replay, legacy adapters, shifted grids, same-slot and same-key contention, actual clock after a lock wait, closure/reservation races, schedule revision races, rejected-key recovery, audit failure and receipt failures. Deliberate database fault tests log expected 500 errors. The memory engine lacks rollback: receipt assertions requiring rollback are PostgreSQL-only.

## Local rollout

Run `npm run migration:run`, then `npm run schedule:preflight`. The preflight is read-only and reports center IDs and aggregate existing-arrival counts without customer details. Invalid schedule data yields exit 1; valid schedules with affected existing bookings need staff review. Initial settings are zero notice and seven India calendar dates including today. Existing booking times are never rewritten.

Manager: More → Working hours & booking slots. Customer: booking → schedule. Arrival slots are not repair-duration or bay reservations. See `development-documents/architecture/pending-scopes/af-009-booking-hours-and-slot-availability.md` in the parent workspace for the full contract and remaining scope.
